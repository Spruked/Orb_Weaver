# Pointer Plot Map Live Validation

Orb Weaver already extracts candidate pointer identities during the crawl and captures repeated desktop/mobile browser renders during Pointer Recovery. The live-validation command connects those existing systems into one explicit operator workflow.

## Purpose

Use this after a full or scoped crawl has generated a fresh `pointer_plot_map.json`.

The command:

1. Loads the baseline Pointer Plot Map.
2. Derives the unique public routes represented by the map.
3. Uses Playwright to render each route twice at desktop and mobile viewport sizes.
4. Resolves the live DOM/accessibility candidates.
5. Reconciles candidates against the baseline records.
6. Classifies each record as static, responsive, dynamic, deferred, conditional, or unknown.
7. Stores compact observed rectangles as evidence-only recovery hints.
8. Moves highly repeated generic topic aliases into a page-level shared dictionary.
9. Writes a validated map and a machine-readable validation report atomically.

## Critical coordinate boundary

Observed rectangles are **not pointer authority**.

Every generated `visual_recovery_hint` contains:

```json
{
  "authority": "evidence_only",
  "may_drive_pointer_action": false,
  "requires_live_dom_or_accessibility_verification": true
}
```

The runtime may use this evidence to narrow a localized recovery search. It must still resolve a live DOM or accessibility target before moving, pointing, navigating, or acting. Fixed coordinates never replace target identity.

## Screenshot metadata and bounded OCR recovery

Pointer Recovery captures viewport screenshots together with the geometry needed
to interpret visual evidence:

```json
{
  "scroll_x": 0,
  "scroll_y": 480,
  "viewport_size": {"width": 1440, "height": 900},
  "screenshot_size": {"width": 1440, "height": 900},
  "device_pixel_ratio": 1,
  "scale_x": 1,
  "scale_y": 1
}
```

OCR boxes are measured in screenshot pixels, converted through `scale_x` and
`scale_y` into viewport CSS coordinates, and then offset into document CSS
coordinates using `scroll_x` and `scroll_y`. The scales are recorded from the
actual screenshot dimensions rather than inferred from device-pixel ratio, so
unexpected rendering scale is visible in the evidence.

The recovery path may run a bounded Tesseract witness over captured segments.
It requests TSV output explicitly with `-c tessedit_create_tsv=1` and retains
only text, confidence, pixel bounds, and block/line identifiers needed to
compare OCR lines with existing DOM candidate rectangles. OCR can narrow an
ambiguous candidate set, but it cannot promote a candidate:

```json
{
  "authority": "evidence_only",
  "may_drive_pointer_action": false
}
```

The existing repeated-render, durable-identity, and exact-one live-target
verification remains the only promotion path. Missing `segments` metadata in an
older capture leaves the recovery run DOM-only; it does not trigger an inferred
coordinate transform.

The executable and model directory are explicit service configuration:

```text
TESSERACT_CMD=/home/bryan/substrate/orb_vision/tesseract/bin/tesseract
TESSDATA_PREFIX=/home/bryan/substrate/orb_vision/tesseract/share/tessdata
```

The Docker image and compose service use the in-image equivalents
`/usr/bin/tesseract` and `/usr/share/tesseract-ocr/5/tessdata`. The separate
`ORB_WSL_TESSERACT_BIN` setting remains confined to the Desktop OCR path.

## Command

Run from the Orb Weaver repository root:

```bash
python scripts/validate_pointer_plot_map.py \
  --base-url https://campaign.orbweaver.spruked.com \
  --map /path/to/campaign/client/current/pointer_plot_map.json
```

The default output directory is:

```text
<map parent>/validation/
```

Generated files:

```text
validation/
├── browser_capture/
│   ├── browser_capture.json
│   └── route-*.png
├── pointer_plot_map.validated.json
└── pointer_validation_report.json
```

To publish only after reviewing the report:

```bash
python scripts/validate_pointer_plot_map.py \
  --base-url https://campaign.orbweaver.spruked.com \
  --map /path/to/baseline/pointer_plot_map.json \
  --publish /path/to/authoritative/pointer_plot_map.json
```

The publish write is atomic. The original map remains untouched unless `--publish` is supplied.

## Reuse an existing capture

```bash
python scripts/validate_pointer_plot_map.py \
  --base-url https://campaign.orbweaver.spruked.com \
  --map /path/to/baseline/pointer_plot_map.json \
  --capture /path/to/browser_capture.json
```

This is useful when screenshots and browser evidence were already generated by a scan run.

## DOM mutability meanings

| Value | Meaning |
|---|---|
| `static` | Identity, content, and geometry remained stable across repeated renders. |
| `responsive` | Identity remained stable, but geometry changed by viewport. |
| `dynamic` | Identity was recoverable, but locator or content changed across renders. |
| `deferred_js` | The target appeared in only one observed render. |
| `conditional` | The target appeared in some, but not all, expected renders. |
| `unknown` | No matching live observation was found. |

Mutability is evidence about rendering behavior. It does not independently grant pointer permission.

## Alias compaction

The optimizer moves only a topic alias repeated on at least 70% of a page's records, with a minimum of five occurrences. Direct target aliases remain on every record.

This removes patterns such as repeating `information about website` hundreds of times while preserving target-specific phrases such as `open Founding Beta` or `find Investor Contact`.

Shared page topics are stored in:

```json
{
  "shared_topics_by_page": {
    "https://example.com/": ["information about website"]
  }
}
```

Page-level shared topics are context for Site World and cognition. They should not be used to select one specific pointer target because they are intentionally non-discriminating.

## Acceptance checks

The validation report must show:

- every visual recovery hint has `may_drive_pointer_action: false`;
- no duplicate target IDs were introduced;
- validated record count equals the intended authoritative record count;
- `CONFIRMED` and `DYNAMIC` records came from repeated live evidence;
- unresolved records remain non-pointable;
- route, viewport, and rendering evidence are preserved;
- OCR evidence, when present, is bounded and explicitly non-authoritative;
- the baseline file was not overwritten unless the operator explicitly published it.
